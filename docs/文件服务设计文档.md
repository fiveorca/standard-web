# 项目开发提示词：通用文件系统服务（File System Service）

## 一、项目目标

请你扮演一名资深 Java 架构师和高级后端工程师，设计并实现一个通用文件系统服务（File System Service）。

该系统属于互联网基础设施服务，定位为独立的文件存储与管理中间件，为其他业务系统提供统一的文件存储、文件管理、文件访问、临时授权、文件去重和存储生命周期管理能力。

系统必须支持多种物理存储后端，业务系统不需要关心文件实际存储在本地磁盘、Amazon S3 还是阿里云 OSS，只需要通过统一 API 使用文件服务。

系统应采用模块化设计，未来能够独立部署，也能够方便地集成到其他互联网项目中。

不要只生成项目骨架或示例代码，需要实现完整、可运行、可测试的业务功能。

## 二、技术栈

使用以下技术栈：

- Java 25
- Spring Boot 4.1.x
- Spring Cloud 2025.1.x
- Spring Framework 7.x
- Maven
- Spring MVC
- Spring Security（按需集成认证授权）
- Spring Validation
- Spring JDBC（优先使用 JdbcClient 或 NamedParameterJdbcTemplate）
- PostgreSQL 作为默认关系型数据库
- Flyway 数据库版本迁移
- Jackson 3，遵循 Spring Boot 4 的默认依赖管理
- OpenAPI 3
- Micrometer + OpenTelemetry 可观测性支持
- JUnit 5
- Testcontainers

版本要求：
1. 使用正式 GA 版本，不使用 SNAPSHOT、MILESTONE、RC 版本。
2. Spring Boot 和 Spring Cloud 必须使用官方兼容的版本组合。
3. 使用 Spring Boot BOM 和 Spring Cloud BOM 管理依赖版本。
4. Spring Framework 由 Spring Boot 管理，不要随意手动指定版本。
5. 不得引入与 Spring Boot 4 不兼容的第三方依赖。
6. Spring Cloud 仅引入实际需要的组件，不为了使用技术栈而强制引入不必要的微服务组件。

## 三、核心架构设计

采用模块化单体架构（Modular Monolith），保证项目可以独立运行，同时具备后续拆分和扩展能力。

建议按照职责划分代码：

- bootstrap：应用启动和自动配置
- interfaces：REST API、请求响应 DTO
- application：应用服务、业务流程编排
- domain：核心领域模型、业务规则、接口定义
- infrastructure：数据库、对象存储 SDK、文件系统、定时任务等基础设施实现
- shared：公共异常、响应结构、工具类和公共模型

核心设计原则：

1. 业务逻辑不能直接依赖 AWS S3 或阿里云 OSS SDK。
2. 必须通过统一的存储抽象接口访问不同存储后端。
3. 文件对象和文件记录必须分离。
4. 物理文件的生命周期与业务文件记录的生命周期必须分离。
5. 文件去重必须基于真实文件内容，而不是文件名称。
6. 所有重要操作必须具备幂等性。
7. 文件上传、文件迁移、物理删除必须考虑并发和失败恢复。
8. 任何业务模块都不能直接访问底层文件存储路径。

## 四、文件存储后端管理

### 4.1 统一存储抽象

定义统一的 StorageProvider 接口，封装不同存储介质的操作。

至少提供以下能力：

- 上传文件
- 上传临时文件
- 临时文件迁移到永久存储
- 下载文件
- 删除文件
- 检查文件是否存在
- 获取文件元数据
- 遍历存储文件
- 创建临时上传授权
- 创建临时下载授权
- 创建分片上传任务
- 完成分片上传
- 取消分片上传
- 检查存储后端连接状态

通过适配器模式实现不同的存储提供者。

### 4.2 必须实现的存储提供者

第一阶段至少支持：

1. Local Storage：本地文件系统。
2. Amazon S3：通过 AWS SDK 实现。
3. Aliyun OSS：通过阿里云 OSS SDK 实现。

同时应预留扩展能力，方便未来支持：

- MinIO
- Cloudflare R2
- Google Cloud Storage
- Azure Blob Storage
- 其他 S3 兼容对象存储

不同存储提供者必须采用独立适配器实现，不能将 S3 和 OSS 的实现代码混杂在业务层。

### 4.3 存储配置管理

支持在数据库中维护多个存储提供者实例。

例如：

- local-default
- s3-us-east
- s3-ap-southeast
- aliyun-oss-cn-hangzhou
- aliyun-oss-cn-shanghai

每个存储提供者需要支持配置：

- 唯一标识
- 存储名称
- 存储类型
- Endpoint
- Region
- Bucket
- 存储根路径或 Prefix
- Access Key
- Secret Key
- 是否启用
- 是否作为默认存储
- 是否允许上传
- 是否允许下载
- 是否允许删除
- 创建时间
- 更新时间

安全要求：

1. Access Key 和 Secret Key 不能明文存储。
2. 敏感配置优先从环境变量、密钥管理服务或加密配置中获取。
3. 数据库仅保存必要的配置引用或加密后的凭据。
4. 不能通过普通查询 API 返回敏感信息。
5. 修改存储配置后应支持连接测试。
6. 禁止将云厂商永久密钥直接返回给客户端。

## 五、文件上传与存储生命周期

### 5.1 普通文件上传

支持普通文件上传，文件首先进入临时存储区，而不是直接进入永久存储区。

上传流程：

1. 客户端请求创建上传任务。
2. 服务端生成唯一 uploadId 和 fileId。
3. 服务端根据存储配置选择临时存储位置。
4. 客户端上传文件。
5. 服务端记录上传状态及必要的文件元数据。
6. 上传完成后，文件处于待确认状态。
7. 客户端调用确认接口。
8. 服务端验证文件完整性、计算 SHA-256。
9. 检查永久存储区是否已经存在相同内容的文件。
10. 如果已存在，则直接关联已有文件对象，并清理临时文件。
11. 如果不存在，则将临时文件迁移到永久存储区。
12. 更新数据库文件对象及文件记录状态。
13. 返回正式文件标识。

文件上传必须支持：
- 普通上传
- 大文件上传
- 分片上传
- 上传超时
- 上传中断恢复
- 上传任务过期
- 上传任务取消
- 重复请求幂等处理

### 5.2 临时存储和永久存储

必须严格区分临时存储和永久存储。

建议采用独立的目录或 Bucket Prefix：

```text
storage/
├── temporary/
│   ├── upload-session-001
│   └── upload-session-002
└── permanent/
    ├── 2026/
    │   ├── 01/
    │   └── 02/
    └── ...
```

要求：

1. 临时文件必须有过期时间。
2. 未确认的文件不能进入正常文件列表。
3. 确认文件时才执行正式存储迁移。
4. 迁移失败必须能够重试。
5. 迁移过程需要有明确的状态记录。
6. 不允许因为服务进程异常而产生无法追踪的文件。
7. 本地磁盘和对象存储必须分别实现适合自身特性的迁移逻辑。
8. 对象存储优先使用服务端 Copy Object 等原生能力，不能无必要地下载再重新上传。
9. 迁移必须考虑跨 Bucket、跨存储提供者的情况。
10. 不同存储后端不支持原子移动时，必须使用可恢复的状态机保证最终一致性。

## 六、文件唯一标识与内容去重

必须实现文件内容去重。

设计要求：

### 6.1 两种唯一标识

区分：

- fileId：文件记录的唯一标识，建议使用 UUIDv7 或其他全局唯一 ID。
- contentHash：文件内容哈希，采用 SHA-256。

不能直接使用 SHA-256 作为对外的文件 ID。

### 6.2 去重逻辑

上传文件时，根据实际文件内容计算 SHA-256。

查询相同存储范围内是否已经存在对应的永久文件对象。

如果存在：

- 不重复写入物理文件。
- 创建新的文件记录或关联已有文件对象。
- 清理此次上传的临时文件。
- 返回新的 fileId 和原有 fileObjectId。

如果不存在：

- 正常迁移文件。
- 创建文件对象。
- 创建对应的文件记录。

要求：

1. 数据库必须通过唯一约束保障并发情况下的去重正确性。
2. 不能只依靠先查询、再插入的应用层判断。
3. 考虑不同文件同时上传造成的竞争。
4. 不同存储提供者之间是否去重应由存储策略决定。
5. 默认在同一存储空间内进行物理去重。
6. 同一物理文件可以关联多条业务文件记录。
7. 文件名称不同但内容相同，仍然应该去重。
8. 文件记录应保留各自的原始文件名。

不能盲目信任客户端传递的 SHA-256，必须服务端计算，或通过可靠的对象存储校验机制验证。

## 七、文件记录管理

文件记录用于描述业务系统对文件的引用关系，不等同于物理文件。

一份物理文件可以对应多个文件记录。

每条文件记录至少包含：

- fileId
- fileObjectId
- 原始文件名
- 文件展示名称
- 文件大小
- MIME Type
- 文件扩展名
- 文件来源类型
- 来源系统标识
- 来源业务标识
- 业务关联 ID
- 创建者
- 租户标识（预留）
- 文件状态
- 创建时间
- 更新时间
- 删除时间

### 7.1 来源管理

支持区分不同文件来源。

例如：

```text
用户中心：
sourceType = USER
sourceId = 10001

订单系统：
sourceType = ORDER
sourceId = 20001

商品系统：
sourceType = PRODUCT
sourceId = 30001

后台管理系统：
sourceType = ADMIN
sourceId = 40001
```

来源字段必须具有扩展性，不能在代码中写死所有业务来源。

支持：

- 来源类型管理
- 来源系统管理
- 来源标识查询
- 按来源查询文件
- 按业务 ID 查询文件
- 批量关联文件
- 文件记录状态管理
- 文件来源统计

需要区分两个概念：

- Storage Provider：文件实际存放在哪里。
- File Source：文件属于哪个业务系统或业务场景。

二者不能混淆。

### 7.2 文件记录和物理文件删除

删除文件记录与删除物理文件必须分开处理。

删除一条文件记录时：

1. 删除或软删除对应的文件记录。
2. 检查对应物理文件是否还存在其他有效引用。
3. 如果仍有其他文件记录引用，不删除物理文件。
4. 如果已经没有有效引用，则将物理文件标记为待回收。
5. 交由物理文件清理任务执行最终删除。

必须防止删除一个业务来源的文件记录，导致其他业务系统无法访问同一物理文件。

## 八、S3、阿里云 OSS 等外部存储临时授权

这是本项目的重要功能。

除了服务端中转上传，还必须支持客户端直接上传到对象存储。

即文件服务只负责管理存储配置、授权申请、文件记录和元数据，不负责传输文件内容。

### 8.1 授权申请流程

例如，业务系统需要上传一张图片到阿里云 OSS：

1. 客户端向文件服务申请上传授权。
2. 文件服务根据指定的 Storage Provider 确定存储位置。
3. 创建一条待上传的 File Object 记录和 File Record。
4. 创建上传任务。
5. 通过对应的存储适配器申请临时授权。
6. 将临时上传授权返回给客户端。
7. 客户端直接将文件上传到 OSS。
8. 文件服务不接收、不转发文件内容。
9. 客户端上传成功后通知文件服务确认。
10. 文件服务通过对象存储 HEAD 等接口检查对象是否存在、大小和元数据。
11. 验证文件信息后，将记录状态更新为正常。
12. 此后通过统一文件 API 管理这个文件。

S3 和 OSS 必须分别使用适合各自平台的授权方式：

**Amazon S3：**
- Pre-signed PUT URL
- Pre-signed POST Policy
- Multipart Upload 临时签名
- 必要时支持短期 STS 凭据

**阿里云 OSS：**
- STS 临时安全令牌
- 临时上传签名
- Policy / Callback 等适合的上传授权方式
- 分片上传授权

要求：

1. 授权必须限制有效期。
2. 授权必须限制可操作的 Bucket 和 Object Key。
3. 尽可能限制文件大小、上传类型和操作权限。
4. 不能将永久 AccessKey / SecretKey 返回给客户端。
5. 不同云厂商的授权逻辑封装在各自适配器内部。
6. 统一返回授权信息，但允许不同厂商有各自必要的扩展字段。
7. 保存授权申请对应的文件记录及上传任务。
8. 不得因为生成了授权就将文件标记为上传成功。
9. 授权超时、上传失败、确认失败都必须有相应处理机制。
10. 对未完成上传的文件记录进行过期回收。

### 8.2 授权与文件记录分离

需要明确：

生成临时上传授权，不代表文件已经存在。

文件上传前：
- 文件记录状态为 PENDING_UPLOAD。
- 文件对象状态为 PENDING_UPLOAD。
- 不允许正常下载。

文件上传成功并确认后：
- 更新文件对象元数据。
- 更新文件记录状态为 ACTIVE。
- 才允许正常使用。

此流程不能由文件服务代替客户端上传文件。

### 8.3 直接上传和服务端上传统一管理

两种上传模式必须兼容统一文件管理体系。

```text
                文件系统服务
                     |
             创建上传任务/文件记录
                     |
           +---------+----------+
           |                    |
       服务端上传             客户端直传
           |                    |
      临时存储区          S3 / Aliyun OSS
           |                    |
           +---------+----------+
                     |
                  确认上传
                     |
                文件对象管理
                     |
                文件记录管理
```

两种模式最终都应该形成统一的文件对象与文件记录。

## 九、定时清理与存储一致性检查

必须实现后台定时任务，自动检查并清理永久存储区中的孤儿文件。

核心要求：

### 9.1 孤儿文件清理

定时遍历永久存储区中的实际文件。

对比数据库中的物理文件对象记录。

如果发现：

- 存储中存在文件；
- 数据库中不存在对应的有效 File Object 记录；
- 文件已经超过配置的安全等待时间；

则将其认定为孤儿文件，执行清理。

### 9.2 清理机制

必须考虑以下情况：

1. 分页遍历对象存储，不能一次加载所有文件。
2. 支持本地文件系统遍历。
3. 支持 S3 ListObjectsV2。
4. 支持 OSS 对象列表分页。
5. 排除临时存储区。
6. 排除正在上传、迁移和删除的文件。
7. 排除未完成的 Multipart Upload。
8. 配置孤儿文件保留时间，避免刚上传的文件被误删。
9. 删除前再次检查数据库。
10. 支持清理失败重试。
11. 支持清理任务执行日志。
12. 支持配置每次最大清理数量和执行速率。
13. 支持只扫描、不删除的 Dry Run 模式。
14. 支持分布式部署情况下的任务互斥。
15. 清理任务不能影响正常文件读写。

### 9.3 双向一致性检查

除了清理存储中没有数据库记录的文件，还需要反向检查：

- 数据库存在文件对象记录，但物理文件不存在。
- 文件记录引用了不存在的文件对象。
- 文件对象没有任何有效文件记录。
- 已删除的文件对象仍然残留在存储中。
- 处于迁移状态但长时间没有完成的文件。

对于发现的不一致数据，应根据具体状态选择修复、重试、标记异常或告警，不能盲目删除数据库记录。

### 9.4 安全删除原则

物理文件删除必须具备：

- 待删除状态
- 删除前二次确认
- 引用关系检查
- 延迟删除机制
- 删除操作日志
- 失败重试机制

不能简单地通过文件名或对象 Key 与数据库比较后立即删除。

## 十、数据库设计

需要设计完整的关系型数据库表结构，并使用 Flyway 管理数据库迁移。

至少包括以下表：

### 1. storage_provider

存储提供者配置表。

管理 Local、S3、OSS 等不同存储实例。

### 2. file_object

物理文件对象表。

管理真正存储在磁盘或者对象存储中的文件。

关键字段：

- id
- storage_provider_id
- object_key
- sha256
- file_size
- mime_type
- storage_status
- created_at
- updated_at
- deleted_at

需要设计合适的唯一约束，避免并发情况下产生重复物理文件。

### 3. file_record

业务文件记录表。

管理文件来源、业务关联、原始文件名及文件元数据。

### 4. upload_session

上传任务表。

管理普通上传、临时上传、分片上传及直接授权上传。

### 5. file_source

文件来源管理表。

管理业务来源及来源系统信息。

### 6. storage_operation_log

存储操作日志表。

记录上传、迁移、删除、授权、文件检查等关键操作。

### 7. file_cleanup_task

文件清理任务表。

管理孤儿文件扫描、物理文件回收及失败重试。

数据库设计要求：

1. 提供完整 DDL。
2. 正确设置主键、外键和唯一约束。
3. 根据查询场景创建索引。
4. 避免不必要的冗余字段。
5. 文件记录与文件对象的关系必须清晰。
6. 文件记录可以独立删除，不能破坏其他文件引用。
7. 上传任务、文件对象、文件记录的状态必须明确。
8. 时间字段统一采用 UTC 存储。
9. 不要将文件二进制内容存进关系型数据库。
10. 必须考虑高并发下的唯一性和数据一致性。

## 十一、REST API 设计

统一使用 `/api/v1` 作为 API 前缀。

至少实现以下接口。

### 1. 存储管理

- 创建存储配置
- 修改存储配置
- 删除存储配置
- 获取存储配置列表
- 获取存储配置详情
- 测试存储连接
- 设置默认存储
- 启用或禁用存储提供者

### 2. 上传管理

- 创建普通上传任务
- 上传文件内容
- 创建分片上传任务
- 上传文件分片
- 查询上传任务
- 完成分片上传
- 取消上传任务
- 确认文件上传

### 3. 文件管理

- 获取文件详情
- 获取文件列表
- 按文件来源查询
- 按业务 ID 查询
- 批量查询文件
- 删除文件记录
- 批量删除文件记录
- 获取文件下载地址
- 获取临时下载授权

### 4. 外部对象存储授权

- 申请 S3 直接上传授权
- 申请 OSS 直接上传授权

- 确认外部上传完成

- 取消外部上传任务

### 5. 清理与运维

- 查询清理任务
- 查询清理历史
- 查询存储空间统计
- 查询各存储提供者使用情况

所有 API 需要提供：
- 请求 DTO
- 响应 DTO

- 统一响应结构
- 统一异常处理
- OpenAPI 文档

不允许直接将数据库 Entity 暴露给 API。

## 十二、文件安全

必须考虑文件系统的安全性。

至少实现：

1. 文件类型白名单配置。
2. 文件大小限制。
3. MIME 类型与实际文件内容校验。
4. 文件名清洗。
5. 防止路径穿越攻击。
6. 防止任意文件覆盖。
7. 生成随机且不可预测的对象 Key。
8. 下载授权有效期限制。
9. 上传授权权限限制。
10. 对重要接口进行身份认证及权限控制。
11. 敏感操作审计。
12. 避免返回真实服务器磁盘路径。
13. 避免公开访问未经授权的私有文件。
14. 支持文件病毒扫描接口扩展。

文件的存储路径不能直接采用客户端传入的文件名。

## 十三、异常处理与可靠性

文件服务需要特别考虑存储操作与数据库事务不属于同一个事务的问题。

必须设计可靠的状态机和补偿机制。

例如：

- 文件已经写入存储，但数据库提交失败。
- 数据库记录已经创建，但文件上传失败。
- 临时文件迁移成功，但状态更新失败。
- 删除文件时对象存储接口超时。
- 客户端上传成功，但没有调用确认接口。
- 服务进程在上传过程中异常退出。
- 重复提交确认请求。
- 多个客户端同时上传相同文件。

要求：

1. 重要操作使用状态机管理。
2. 物理存储操作不能假定与数据库事务原子提交。
3. 对外部存储操作实现超时和有限重试。
4. 失败任务支持恢复执行。
5. 对无法自动恢复的数据提供运维排查能力。
6. 防止重试产生重复文件和重复删除。
7. 重要操作必须记录操作日志。
8. 禁止使用简单的 catch 后忽略异常方式处理失败。

## 十八、特别强调

以下设计原则是强制要求：

1. 文件对象、文件记录、存储提供者必须是三个独立概念。
2. 不能把业务来源直接当成物理存储位置。
3. 文件唯一性必须基于真实内容哈希。
4. 必须支持一个物理文件被多个业务文件记录引用。
5. 必须支持服务端上传和客户端直接上传对象存储两种模式。
6. S3 和 OSS 临时授权必须采用云厂商的安全授权机制。
7. 临时授权下发不能意味着文件已经上传成功。
8. 定时清理必须具备保护机制，不能误删正常使用的文件。
9. 删除文件记录不等于立即删除物理文件。
10. 存储 SDK 必须封装在独立适配器中。
11. 新增存储后端时不能修改文件核心业务逻辑。
12. 不允许只生成接口定义或伪代码，必须交付实际实现。
13. 不允许为了赶进度省略异常处理、数据库约束和测试。
14. 不允许出现大量 TODO、空方法或假实现。

最终目标：

构建一个类似通用基础设施的文件系统服务，能够被用户中心、订单系统、商品系统、内容系统、后台管理系统等不同业务服务共同使用。

业务系统只需要通过统一 API 上传、关联、查询、下载和删除文件，无须了解文件底层存储方式。

系统未来可以独立扩容、独立部署，并且能够通过新增 StorageProvider 适配器支持更多存储厂商。
