# 一、整体架构要求

## 1. 技术栈

两个服务统一使用以下技术体系：

- 编程语言：Rust Stable。
- Web 框架：Axum，优先使用当前稳定且兼容的版本。
- 异步运行时：Tokio。
- 数据库：优先沿用当前项目已经确定的数据库；如果没有明确约定，使用 PostgreSQL。
- ORM / 数据访问：优先采用 SQLx，使用异步数据库访问。
- 缓存：Redis。
- 序列化：Serde。
- 配置：支持 TOML、环境变量配置。
- 日志：Tracing。
- API 文档：OpenAPI 3.1，集成 Swagger UI。
- 数据库迁移：SQLx Migrations。
- 容器部署：Docker。
- 接口风格：RESTful API，统一 JSON 响应格式。
- 身份认证协议：OAuth 2.0、OpenID Connect 1.0、SAML 2.0。
- 密码安全：Argon2id。
- MFA：TOTP、WebAuthn/Passkeys，并预留短信和邮件验证码适配接口。

使用成熟、活跃维护、许可证兼容的开源依赖。

选择依赖时必须检查实际 API、兼容性、安全状态和许可证。不得因为某个 Crate 名称相似，就假定它具有完整的协议实现能力。

对于 OAuth2/OIDC/SAML 等标准协议，必须依据标准规范实施，不能通过自行定义几个 HTTP 接口冒充协议支持。

# 四、两个中心之间的协作规范

必须实现清晰且可落地的服务协作机制。

## 1. 数据所有权

认证中心的数据由 auth 管理。

包括：

- 身份账户。
- 密码及凭证。
- 认证会话。
- Token。
- OAuth 客户端。
- MFA。
- 身份联邦。
- 角色和权限。
- 授权策略。
- 用户角色关联。
- 角色权限关联。

用户中心的数据由 user 管理。

包括：

- 用户个人资料。
- 用户扩展属性。
- 用户分组。
- 组织和部门。
- 用户组织关系。
- 用户业务状态。
- 用户注册业务资料。
- 用户资料与认证账户的映射。

禁止两个中心同时维护同一份数据的权威副本。

手机号和邮箱在认证中心负责验证凭证和登录身份，在用户中心负责个人业务资料展示；需要通过事件保持状态一致，不得分别形成冲突的验证结论。

## 2. ID 规范

统一使用全局唯一且不可变的用户 ID。

认证中心创建身份主体后，用户中心使用同一个 ID 创建用户资料。

不能依靠用户名、手机号、邮箱作为两个中心之间的关联主键。

## 3. 注册一致性

设计可靠的跨服务注册机制：

1. 创建认证身份。
2. 创建对应用户资料。
3. 保证操作具备幂等性。
4. 处理服务调用失败。
5. 支持失败重试。
6. 支持状态补偿。
7. 防止重复注册。
8. 通过 Outbox / Inbox 或等价的可靠事件机制保障最终一致性。

不要假设两个服务的数据库可以进行分布式事务。

## 4. 事件通信

优先支持可靠事件模型。

至少定义以下事件：

- auth.identity.registered
- auth.identity.activated
- auth.identity.disabled
- auth.identity.deleted
- auth.identity.restored
- auth.identity.credentials_changed
- auth.user_roles.changed
- auth.permissions.changed
- auth.tenant_membership.changed
- user.profile.created
- user.profile.updated
- user.profile.deleted
- user.organization.changed
- user.group.changed
- user.account_status.changed

事件必须包含：

- event_id。
- event_type。
- aggregate_id。
- occurred_at。
- version。
- trace_id。
- payload。

事件消费必须幂等，提供失败重试和死信处理能力。

如当前项目没有消息中间件，先通过数据库 Outbox 和可替换消息发布接口实现可靠机制，不要引入一个强制依赖的复杂消息集群才能启动服务。

## 5. 服务间 API

设计内部 API：

- 创建认证身份。
- 更新认证身份。
- 禁用认证身份。
- 注销认证身份。
- 查询身份状态。
- 查询身份基本信息。
- 用户资料初始化。
- 用户资料状态同步。
- 用户组织变化通知。
- 用户分组变化通知。

内部接口必须使用服务身份认证，不能因为属于内部网络就免除认证和授权。

# 七、Rust 工程质量要求

两个服务都必须采用清晰的分层架构。

建议遵循：

- API Layer：HTTP 路由、请求和响应。
- Application Layer：业务用例、事务编排。
- Domain Layer：领域模型和业务规则。
- Infrastructure Layer：数据库、Redis、外部服务。
- Middleware Layer：认证、授权、限流和安全防护。

具体要求：

1. Handler 不能承载复杂业务逻辑。
2. Repository 负责数据访问。
3. Service / UseCase 负责业务流程。
4. DTO 与数据库实体分离。
5. 错误类型统一管理。
6. 所有数据库操作采用异步方式。
7. 避免不必要的全局状态。
8. 合理处理事务。
9. 合理使用 Arc 和依赖注入。
10. 不允许使用大量 unwrap、expect 掩盖可能发生的运行错误。
11. 不允许在业务代码中到处硬编码配置。
12. 不允许使用内存 HashMap 代替正式数据库实现核心业务。
13. 不允许出现没有真实业务实现的空接口。
14. 不允许使用伪造的 Token 或固定用户身份完成测试。

保持模块高内聚、低耦合。
